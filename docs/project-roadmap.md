# 项目总目标与两阶段路线

2026-10-12 用户明确：先实现与旧项目对等，再优化实现为完整的 Revit 自动化助手。

## 第一阶段：与旧项目功能对等

承接旧项目已经具备的自动化能力，以 `legacy-feature-matrix.md` 和 `mcp/legacy-source-matrix.json` 为逐项来源清单。对等以实际业务结果和自动化流程为依据，不以接口数量、编译成功或工具可发现作为完成标准。

逐项完成实现、原生结果核验，以及适用的失败回滚、保存后复查和副作用检查。只读能力按只读合同验收。旧版未实现的代码、探针和参考脚本不冒充成熟业务功能；需要重新设计或尚未暴露的旧能力必须明确说明替代路径和缺口，不能直接算作对等完成。

本阶段优先补齐迁移及验收缺口，形成可稳定使用的版本。既有逐项验收记录继续有效，本目标确认不改变任何能力的当前验收状态。

## 第二阶段：完整的 Revit 自动化助手

在功能对等的基础上优化易用性、可靠性和自动化程度，逐步覆盖 Revit 各类功能，使用户能用自然语言提出任务，由助手读取上下文、澄清必要输入、规划、执行并核验多步骤流程。

覆盖目标包括建筑、结构、机电、族编辑、参数与类型管理、视图与图纸、标注与明细表、导入导出、项目协作及文件生命周期。该列表是扩展方向，不表示这些能力已经实现或已经验收。

后续建立 Revit 功能覆盖清单，逐项记录未支持、已实现、实机验收通过及限制；调查各功能的实现路径，无法自动完成的部分明确披露。完整助手的完成判断以覆盖清单和端到端实际任务验收为依据，不以旧项目对等替代全功能覆盖。

## 生产入口架构：MCP 与独立后台入口并行

生产实现采用同一套 Revit API 领域核心和模型构建器，提供两种入口：

1. **MCP 交互入口**：面向自然语言任务，负责读取上下文、澄清输入、生成预览、取得聊天确认、执行并核验。该入口保留现有文档身份、revision、计划确认、回滚和保存边界。
2. **独立后台入口**：面向批处理、队列、定时任务和系统集成，由 CLI、HTTP 或任务队列提交结构化建模任务。后台入口复用同一套类型解析、几何校验、事务执行和结果核验逻辑，通过 Revit API 运行环境打开模板或测试副本，生成并保存独立 `.rvt` 文件。

独立后台入口不直接伪造或解析写入 `.rvt` 二进制格式；它仍然需要 Autodesk Revit API 的运行宿主，例如独立 Revit 插件、RevitCoreConsole 或 Autodesk Design Automation。MCP 是交互编排层，后台入口是生产执行层，两者共享模型能力但不互相绑定。任何入口都必须记录输入、模板/版本、任务状态、输出路径、元素统计和保存后核验结果。

### 独立后台入口建设顺序

1. 抽取与 MCP 无关的领域核心：单位转换、标高/墙/楼板/柱/门窗等结构化操作模型、类型解析、几何和参数校验。
2. 建立单机后台运行器：接收 JSON 任务，启动或连接受支持的 Revit API 宿主，执行单任务事务并另存为目标 `.rvt`。
3. 增加任务状态和幂等键：支持排队、取消、失败回执、重试边界和输出文件校验，禁止重复提交造成重复模型。
4. 增加服务化入口：在 CLI 验收通过后，再提供 HTTP/队列适配器；入口层只负责调度，不复制 Revit 建模逻辑。
5. 完成生产验收：模板隔离、版本匹配、并发限制、进程退出、保存后重开、元素统计和失败回滚均有独立证据。

当前状态：独立后台入口已纳入生产路线，尚未完成独立运行器、部署方式和端到端生产验收。现有 MCP + Revit API 能力不自动视为后台入口完成。

### 最终产品形态：Revit 内置插件 + 多驱动入口

最终产品以 Revit 内置插件为主体。插件内提供 AI 助手配置，首版支持 OpenAI 兼容接口和自定义 JSON 接口，并支持插件直连 AI 或通过本机助手服务转发。

Claude Code、Codex、DeepSeek Harness、Pi 等外部 Agent/Harness 通过 MCP、stdio、HTTP 或本机服务调用同一套结构化建模协议。它们负责理解需求和编排任务，Revit 插件负责唯一的模型读取、计划校验、事务写入、保存和结果核验入口。

产品公开发布到 GitHub。仓库提供 `AGENTS.md`、版本清单、只读 preflight、安装、验证和回滚脚本，使 Agent 能识别本机 Revit 版本、选择匹配 Release、在用户批准后安装并完成实载验证。密钥、RVT 文件和本机验收证据不进入仓库。

该产品形态优先于单独制作一个脱离 Revit 的大软件；桌面配置和后台任务能力作为插件配套组件逐步增加。

## 推进原则

先完成第一阶段，再系统推进第二阶段。第一阶段允许补充为迁移和验收所必需的基础能力；新增扩展需求记录到第二阶段，避免无限扩大第一阶段的完成范围。

自动化目标不替代必要的工程输入和判断，也不改变已有执行授权规则；本文件不是部署、模型写入、保存或重启的具体执行批准。

## 统一任务流程

完整基础建模能力继续作为项目目标。所有能力采用“登记 → 契约 → 核心实现 → 模拟测试 → 隔离编译 → 只读实机基线 → 预览 → 确认 → 单次执行 → 原生回读 → 保存/重开 → 归档”的生命周期。各专业分线共享同一状态名、运行证据 schema 和完成门槛，不再重复设计验收方法。

流程细则见 [development-flow.md](development-flow.md)，单项任务使用 [capability-task-template.md](capability-task-template.md)。当前任务状态和优先顺序以 [capability-task-queue.json](capability-task-queue.json) 为唯一来源；旧版功能矩阵仍保留原验收结论。
