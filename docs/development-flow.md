# Revit 基础建模能力开发与验收流程

本流程适用于建筑、结构、机电、电气、图纸、族和导入能力。项目继续追求完整的 Revit 基础建模覆盖；本文件只统一推进和验收方法，不缩小功能范围。

## 当前自主推进与合批约定（2026-10-29）

用户最新要求：“以后我不再进行批准，你自己审批，除了需要我手动重启revit，重载mcp插件，重启codex，关闭重新打开隔离副本外，开发过程中一切权限和批准由你做主。在我开启ultra模式的时候建议多发验收，可以多模块，目的是减少我手动操作的过程。”本约定取代旧的项目自设逐次设计/注册确认；当前工具的明确调用约束仍须满足。

- 普通开发决定、源码修改、相关测试、隔离编译、只读验收及证据整理自主推进，不重复请求确认。先汇总同一DLL可验收的模块，再决定加载时机。
- 插件注册可在长期用户授权下由代理逐构建复核。`registration-switch.ps1 -AgentReviewed -StandingAuthorizationPath <私有授权JSON> -ExpectedRequestSha256 <本次复核摘要>` 保留精确请求/模块/清单/备份/保护设置和单次attempt检查；回执标记代理复核，`humanChatApproval=false`，不能冒充用户逐次批准。默认旧人工模式仍可用，两个来源不得混用。授权只涵盖该项目和目标清单；注册过程中授权变化会阻止提交，创建其`.revoked`标记则撤销后续使用。
- Revit程序重启、MCP重载、Codex重启、隔离模型关闭重开仍提示用户完成。没有相应变化就不要求这些操作；Node/schema未变不要求MCP重载，只读任务不要求模型保存重开。
- 用户希望其余事项均可自主处理，包括不再把保存列为人工例外。但当前`revit_custom`仍要求对具体模型planId及生命周期保存预览进行用户聊天批准；长期授权不能冒充该具体批准。普通计划不会保存，旧失败生命周期不恢复或重试。工具兼容的自主保存尚未实现，遇到该边界须明确说明，不能宣称“四项以外已全部自动化”。
- Ultra或用户明确要求高强度推进时，优先在同一DLL/同一会话合批多个独立模块的只读验收，按模块保留结果；不要为凑数量重测。无法获知运行档位时不猜测，日常也沿用合批原则。2026-11-08用户已授权按任务需要选择子代理模型/推理档位；仅在独立工作值得并行时使用，并保持单文件写入归属和主代理最终核验。
- 写入可准备范围明确、依赖已满足、结果可分别核验的多模块批次，当前MCP仍要求批准具体批次planId并仅提交一次。共享宿主/类型/系统或未知副作用无法分离时，继续拆成单能力测试；不把批次通过当成各模块独立或完整工程验收通过。

## 默认精简执行（2026-10-27）

完整生命周期是适用的证据门槛。每轮确定一个交付结果和实际变化范围，复用原任务、契约与证据；按下表选择检查，不因换会话重走全部阶段或另起流程。

| 变更范围 | 本轮检查 | Revit / 加载动作 |
|---|---|---|
| 文档、队列、证据索引 | 格式/引用与相关摘要；矛盾时才读原始证据 | 无，不新建实机run |
| Node算法、错误、摘要 | 受影响单元/CLI；触及MCP契约加SDK检查 | 无DLL动作；需新服务代码时只重连MCP |
| C#规则、原生只读接口 | 对应核心/协议检查及必要的API隔离编译 | 暂存候选，相关修改合批加载 |
| 写入或回读契约 | 对应测试；精确预览、批准、单次提交、原生回读 | 一次一项能力；按持久化目标保存/重开 |
| 候选冻结、发布 | 该批要求的完整回归、编译/CheckOnly、来源冻结 | 逐构建复核后注册，确需实载才手动重启 |

- **先复用。** 查本地，缺口再读1–2处上游代码及相关测试；版本、许可、改动集中在THIRD_PARTY_NOTICES。已有能力不重写，上游结果不代替本项目实机验收。未知字段严格拒绝，不引入任意代码或第二条模型写入通道。
- **合批加载。** C#修改先暂存；失败需返回实际/未知范围，不靠猜名字或宿主推进。相关修复一次注册/加载，不为单个字段立即重启。
- **通过就推进。** 仅新变化、失败或未解疑点触发重测；冻结时再做该批全量检查。只读不套写入11文件profile，不创建模型计划或要求保存重开。入口刷新只查入口和一次目标读取；新SDK不冒充当前聊天入口。
- **保护不重放。** 当前工具要求的精确批准保留，已批准且未变/有效/未提交的对象不再确认。超时先查原attempt/plan/回执，不重建或重放Confirm、保存、注册、写入。输出版本化；手动操作与保存入口的实际限制以本文件最新约定为准。
- **阻塞按依赖。** 未知副作用保留证据、解除条件，继续阻塞依赖该结果的写入；无关离线/只读继续。没有新假设就停止重复追查。受限通过范围与整体blocked分开记。
- **一份事实。** 队列存状态、任务卡存契约/限制、run存原始结果、summary引用产物；只更新变化字段，默认摘要，不复制原始数据或追写递归审查。状态提问不建run。只读基线与未保存写入后回读仍按各自合同区分。

汇报交付、验证、限制和下一步；仅确有必要时提出人工操作。基础建模范围、旧版对等优先顺序、状态名及既有验收结论保持。

## 固定生命周期

每项能力按以下顺序的适用阶段推进；任何确认或模型写入都必须绑定本次运行的当前预览：

- 离线实现/测试/编译以对应源码、日志和构建标识为证据，无须为这些阶段单独连接 Revit。
- 只读能力完成契约、相关测试、必要的插件编译/加载、真实只读核验和归档；不创建模型计划，不要求写入或保存重开。只有图像输出属于声明目标时才增加视觉验收。
- 写入能力按下面完整链路执行。纯 Node 修改不触发 DLL 编译/注册；只读任务不套用已提交写入的 11 文件归档 profile。不适用阶段明确记录为 not-applicable，不伪造通过状态或空文件。

1. **登记**：在 [能力任务队列](capability-task-queue.json) 和来源矩阵中记录能力、专业层、依赖、来源、写入类别、回滚范围和验收范围。
2. **契约**：固定结构化输入、单位/坐标、必填字段、拒绝条件、操作和结果字段。
3. **核心实现**：实现规则、类型解析、几何校验和计划生成；核心逻辑不依赖 Revit 进程。
4. **模拟测试**：运行核心、MCP 契约和失败路径测试；未知值必须显式保留或拒绝。
5. **隔离编译**：用目标 Revit API 编译到带构建标识的独立目录，记录程序集哈希和 MVID；不得覆盖 Revit 锁定的 DLL。
6. **只读实机基线**：在 Revit 当前会话核验插件能力、MVID、文档 identity/revision、保存状态和目标范围。记录本批次实际校验的 MCP 工具契约快照及规范化 SHA-256；每个 scope 工具都必须在快照中声明只读并支持 identity/revision pin。快照用于证据复核，不能替代调用前契约检查。此阶段不创建计划、不写模型。
7. **预览**：以本次基线生成一份 plan，披露精确操作、目标、影响类别、假设、风险、TTL 和回滚范围。
8. **确认**：用户确认与预览摘要完全匹配的具体 plan；记录批准原文、预览哈希和确认调用计数。超时/断线先查询原任务状态。
9. **单次执行**：每次只执行一个明确能力和一个已确认 plan；attempt 标记先落盘，确认调用最多一次，不自动重试。
10. **原生回读**：独立核对原生元素、关键参数/关系、变更收据、警告、删除和额外副作用；未知副作用阻止验收升级。
11. **保存/重开**：用户保存后先做保存后回读；需要持久性验收时再关闭并重开同一文件，比较已声明范围及保存文件摘要。重开后的 session identity 可变化，必须作为新 session 记录。
12. **归档**：将本次证据放入 `acceptance/runs/<runId>/`，更新任务队列的已通过状态、证据引用、限制、阻塞和下一步；历史证据只追加说明，不覆盖。

## 状态模型

所有能力统一使用以下状态名。`currentState` 记录当前门槛；`acceptedStates` 只列已有证据支持的门槛。被阻塞时将 `currentState` 设为 `blocked`，同时保留此前已通过的 `acceptedStates`。视觉验收是单独门槛，不代表整张图纸或其它视图自动通过。代码/测试通过不代表真实 Revit 验收。

- `contract-ready`：输入、输出、拒绝条件和安全边界确定。
- `core-tested`：核心规则、协议和失败路径通过测试。
- `compiled`：目标 Revit API 隔离编译通过。
- `readonly-accepted`：真实 Revit 只读范围核验通过。
- `preview-accepted`：真实 Revit 预览与基线绑定通过。
- `write-accepted`：一次真实写入和原生结果核验通过。
- `persistence-accepted`：保存后或关闭重开核验通过。
- `visual-accepted`：视图/图纸 PNG 或界面结果通过视觉检查。
- `blocked`：存在明确阻塞原因，记录复现证据和解除条件。

每个状态必须链接对应证据：契约引用任务/设计，离线测试和编译引用源码版本、构建标识及日志；真实 Revit 验收引用 `runId`。不为每个离线状态创建空实机 run。历史实机记录没有 `runId` 时保留原样并标记 `archiveStatus=legacy-unindexed`，不可为旧证据伪造新 run。`implemented-and-accepted` 等来源矩阵业务结论保持独立，不由本状态机自动改写。`enabled`、构建成功、工具可发现和模拟测试通过都不能单独升级为已实机验收。

## 依赖顺序

完整功能仍按以下层次推进，减少返工：

1. **基础数据层**：单位、坐标、标高、轴网、类型、文档身份和版本。
2. **建筑主体层**：墙、楼板、屋顶、门窗、房间、洞口、楼梯。
3. **结构层**：柱、梁、基础、结构楼板和连接关系。
4. **机电与电气层**：设备、管道、风管、管件、连接器、灯具、开关、回路和导线。
5. **文档层**：视图、裁剪、图纸、明细表、标签、尺寸和导出。
6. **生命周期层**：保存、重开、版本升级、安装、回滚和发布。

同一层内可以并行开发；跨层能力必须先声明依赖并复用已经验收的基础能力。一个写入计划尽量只覆盖一个功能范围；跨类别组合场景要在各单项通过后另做集成验收。

依赖按本步骤实际需要的子能力和门槛判断。上游 blocked 时，先检查其已通过范围是否已满足当前离线开发或只读步骤；不得仅因上游整体未完成而停止无关开发。房间围护等仍有未解释副作用的实际写入依赖继续遵守原阻塞，不由本规则放行；发布仍检查第一阶段全部必需范围。

## 批处理与恢复规则

- 同一插件 MVID、Revit 会话和文档 revision 的只读查询合并到一个 runId 和一次基线批次；全部 MCP scope 契约先整体预检，每个能力仍保存独立结果片段，基线需有前后上下文复核。未保存的文档只能得到 `unknown` 基线，不能标记 `accepted`。
- 只读批次使用 [readonly-batch.mjs](../mcp/readonly-batch.mjs)：每个 scope 必须是 MCP 声明的非破坏性只读工具，固定插件构建/MVID/PID 与文档 identity/revision；禁止把可创建预览的统一 workflow 入口混入基线。使用方式见 [readonly-batch.md](readonly-batch.md)。
- 写入验收以明确、可回读和可归因的范围分批；可合并依赖已满足的多个模块，不能绕过当前工具的具体planId批准或隐藏未验收类别。无法分别归因的场景继续独立测试。
- 同一程序集版本需要重启加载时，先汇总该版本全部只读验收项，一次人工重启后在同一会话完成；不得为单个只读查询重复注册或重启。
- 编译输出必须使用版本化目录，禁止覆盖 Revit 当前锁定的程序集。
- identity/revision 变化后，旧基线不再绑定新预览；旧 planId 只在原会话、未过期且状态可读时有效。过期计划不能续期或重试。
- 超时、断线或确认响应不明时，先查询原 attempt/plan/执行回执状态；未查清前不得重建或重新确认。
- 插件版本未加载、许可证/宿主不可用、类型或宿主不匹配、用户保存/重开未完成时，记录具体 blocker 和解除条件，不用历史证据代替当前核验。

## 统一证据结构

每次实机运行使用 UUIDv7 `runId`，目录和文件名如下。通过 `node mcp/acceptance-run.mjs init <taskId>` 仅创建新目录与 `manifest.json`；它不连接 Revit，也不生成计划、确认、写入、保存或重启。

```text
acceptance/runs/<runId>/manifest.json       任务、版本、仓库、插件和文档会话
acceptance/runs/<runId>/baseline.json       只读基线
acceptance/runs/<runId>/preview.json        plan、身份/revision、TTL 和影响摘要
acceptance/runs/<runId>/confirmation.json   批准原文、preview 哈希、单次确认计数
acceptance/runs/<runId>/attempt.json        提交前持久化的单次动作标记
acceptance/runs/<runId>/execution.json      attempt、原生执行回执和错误
acceptance/runs/<runId>/readback.json       原生结果、范围差异和副作用
acceptance/runs/<runId>/saved.json          用户保存结果与保存后读取
acceptance/runs/<runId>/reopen.json         关闭重开后的 session 和持久范围核验
acceptance/runs/<runId>/visual.json         图像哈希、尺寸和独立视觉结论
acceptance/runs/<runId>/visual/             PNG 与独立目视复核 JSON
acceptance/runs/<runId>/summary.json        状态门槛、限制、阻塞和证据哈希索引
```

证据字段以 `mcp/run-evidence.schema.json` 为准。失败保留同一 runId 下已产生的阶段、失败阶段、错误、回滚状态和人工后续动作；未发生的阶段在 summary 中标记 `not-applicable` 或 `not-run`，不伪造空证据。每个文件带 `schemaVersion`、`runId`、`taskId`、阶段时间、上游 SHA-256、文档 identity/revision、插件 MVID/DLL SHA-256、只读标志及副作用计数。baseline 额外绑定实际 MCP 工具契约快照与 SHA-256，归档器重新核对 scope、只读注解和两项文档 pin。证据只保留必要模型字段；密钥、RVT 和本机私密配置留在受保护目录。

对已提交、含保存/重开和视觉阶段的标准写入 run，执行 `node mcp/acceptance-run.mjs audit <runId>` 做离线交叉检查。该命令检查 11 份阶段 JSON 的 run/task/plan/attempt 绑定、预览摘要、单次确认计数、文档会话与 MVID、源文件摘要及 PNG 文件头/尺寸；视觉写入前对照按其指明的 source run 查询。发现错配返回非零退出码，既不修复文件也不改变能力验收状态。该检查不是 Revit 实机验收，不适用于只读批次、未完成 run 或失败回滚 run，不能从哈希推出原生结果正确或副作用已清楚。

关闭前保存快照缺失或重开完整原始范围未归档时，报告单独的 limitation，不能用布尔结论补造原始数据。历史 identity 抄录错误用新的 `archive-review-YYYYMMDD.json` 记录原值、权威来源、更正值及上游摘要；原始文件和哈希索引保留。追加更正不会使原始文件离线检查自动通过。未来持久化阶段必须归档实际完整回读对象，供离线重算。

新标准写入记录使用 [共享证据生产函数](acceptance-evidence.md)，由 `mcp/acceptance-evidence.mjs` 固定预览 payload 摘要、manifest 计划绑定、attempt 类型、执行前文档、确认计数及 PNG 实际字节数。函数只生成数据，不提供聊天批准、排他锁或模型执行；调用者仍须按原流程持久化独立 `wx` attempt。schema 已补齐这些字段，归档器保留原有严格绑定、旧记录错误和独立验收结论，不用格式映射替代真实证据。

## 完成门槛

一项写入基础建模能力进入“生产可用”前，必须回答以下问题；只读能力使用前述适用阶段和其只读契约，不要求不适用的写入/保存阶段：

- 能否从统一结构化任务协议调用？
- 缺少类型、宿主、尺寸或坐标时是否明确拒绝？
- 真实 Revit 中是否成功完成预览和一次写入？
- 失败时是否有事务回滚和可读错误？
- 关键元素、参数和关系是否完成原生回读？
- 保存后或关闭重开后是否仍然成立？
- 是否存在额外元素、警告、删除或未知副作用？
- 本阶段已实现且纳入验收的入口是否经过同一执行边界？第一阶段能力不等待第二阶段插件内 AI 或独立后台入口；这些入口实际实现后再做各自合同和集成验收。

任何一项没有证据，就保留为对应的中间状态，不升级为最终完成。
